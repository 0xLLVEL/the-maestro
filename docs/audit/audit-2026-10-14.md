# Audit: blog-kit vs blog-nokit (2026-10-14)

Read-only comparison audit of the two Phase-1 blog builds against the kit standards
(`template/AGENTS.md` and `template/docs/` at `v0.1.1`). Scanner output is heuristics;
every finding below was confirmed by reading the code. Severities follow
`project-audit` (Critical/High/Medium/Low/Info).

Targets: `examples/blog-kit` (branch `example/blog-kit`) and `examples/blog-nokit`
(branch `example/blog-nokit`). Scope: application code, tests, and project docs.
Out of scope: the kit's own scripts, production config, branch protection.

## Verdicts per area

| Area | blog-kit | blog-nokit |
|---|---|---|
| Backend (layering, SoC) | Healthy: routes call `auth.js`/`posts.js` services; no SQL outside them | Partly healthy: single file mixes routing, SQL, HTML, and auth |
| Security | Healthy with notes: hashing, signed sessions, rate limit, validation all present and tested | Messy: exploitable stored XSS plus missing session verification (see AF-001, AF-002) |
| Testing | Healthy: 14/14 tests, 9/9 ACs connected in the PRD-code index | Messy: no tests; one-off smoke script, uncommitted |
| Documentation | Healthy: PRD, screens, progress, index; doc comments 100% of 33 units | Messy: no docs, no file header, one `TODO` left in code |
| API | Healthy: uniform JSON shapes, `/api/v1`, capped pagination | Partly healthy: JSON shapes ad hoc (`{error: 'forbidden'}` strings), fixed page size |
| Git process | Healthy: 8 Conventional Commits on a working branch | Partly healthy: 1 commit, still informative, but no trace of decisions |

## Top findings

1. AF-001 (nokit, High): stored XSS, one-line fix (`escapeHtml`), zero tests would catch a regression.
2. AF-002 (nokit, High): session signatures signed but never verified; the `TODO` is the whole story.
3. AF-006 (kit, Medium): the kit does not prevent guideline breaches; it made this one visible via the scanner.
4. AF-010 (kit, Info): the scanner's highest-severity hit on the kit side is a false positive on safe code — the "heuristics, confirm by reading" contract working as designed.
5. Scanner coverage gap (both): plain-`.html` freestyle output scans as 0 files; auth/CORS/rate-limit rules do not exist, so AF-002/AF-003 were found by human reading, not by script.

## Compliance plan (for the nokit side, if it were to be kept)

- **Phase 0, critical:** none (no leaked secrets; no production data).
- **Phase 1, foundation:** fix AF-001 (escape on output) and AF-002 (verify signatures) first,
  with a regression test each; remove the TODO (AF-007); add the file header (AF-008). Effort: S.
- **Phase 2, structure:** split routing/SQL/HTML into layers; add input validation and login
  rate limiting (AF-003..AF-005) with tests. Effort: M. At this point the result converges
  toward the kit side, which prices the difference.
- **Phase 3, refinement:** design tokens, editorconfig/CI, CHANGELOG. Effort: S.
- Kit side follow-up (separate branch): split `createApp`/`handleApi` (AF-006). Effort: S.

## Method notes

- Scanner runs: `scan.py` on both trees (JSON retained in temp during the audit); all
  heuristic hits opened and read before classification; false positives labeled, not deleted.
- `.env` and secrets: none present in either tree; no secret values are reproduced here.
- No code was changed in either target; the only files written are this report (on the
  audit branch) plus the fix commit for a self-found `comment.prd-reference` violation,
  which predates this audit.
